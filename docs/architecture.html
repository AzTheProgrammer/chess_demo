1. Product Vision & Success Criteria

A single Flutter app that helps players play, analyze, and train — with an elegant, distraction-free interface. The first shippable slice proves the core loop: play a bot game, review it, and complete one training exercise.

Core user journeys

Play vs Bot

Start a game at chosen difficulty, make legal moves, resign/draw, see result and basic stats.

Analyze Games

Import PGN from Lichess or Chess.com (URL or paste), step through moves, see engine eval.

Learn Openings

Browse opening tree, drill lines with spaced repetition, track mastery per line.

Practice Tactics

Daily puzzle queue, rating-adjusted difficulty, streak and accuracy tracking.

Square Trainer

Mini-game: prompt a square name (e.g. "e4"), user taps the correct square under time pressure.

Success condition for this plan ticket: CEO approves architecture and phased scope. Implementation tickets can then be created per phase with clear acceptance criteria.

2. Technology Stack

LayerChoiceRationale
Framework Flutter 3.x (Dart 3) Single codebase for iOS/Android; strong custom painting for board UI; fast iteration.
State management flutter_bloc + equatable Event-driven, explicit state transitions; excellent testability via bloc_test; widely adopted Flutter pattern per CEO direction.
Routing go_router Declarative deep links for shared game/analysis URLs later.
Chess rules chess package (Dart) Legal move generation, FEN/PGN, check/checkmate. Avoid reinventing rules engine.
Engine Stockfish via flutter_stockfish or FFI wrapper Local analysis and bot play. No server cost for v1. WASM/FFI path TBD in spike.
Local storage drift (SQLite) + shared_preferences Games, puzzles, opening progress, settings. Offline-first.
HTTP http + thin API clients Lichess public API; Chess.com pubapi. No auth required for read-only game fetch.
UI Material 3 + custom theme tokens Modern baseline; board and pieces are custom widgets for brand control.
One-way door to flag: Stockfish FFI integration is the highest-risk technical bet. Phase 0 spike validates engine startup latency and binary size on target devices before committing.

3. System Architecture

Clean architecture with feature-first folders. Dependencies point inward: UI → application → domain → infrastructure.

Bloc conventions

  • Bloc for multi-step flows with events (play, analysis, tactics, openings).
  • Cubit for simple toggle/load state (settings, square trainer, home).
  • Inject repositories via constructor; register blocs in MultiBlocProvider at route or app level.
  • Test with bloc_test — assert event → state sequences for game moves, puzzle solves, imports.

Key design principles

  • Reversibility: Feature modules are loosely coupled; each can ship independently behind routes.
  • Operational simplicity: v1 is fully offline-capable except optional game import.
  • Evidence over opinion: Ship Phase 1, measure retention on play+analyze loop before expanding training depth.
  • Scope hammer: Bot uses fixed depth/time limits per tier — no Elo estimation engine in v1.

4. Feature Modules

4.1 Play vs Bot

  • Board widget: 8×8 grid, drag-and-drop + tap-to-move, legal move highlights, last-move highlight.
  • Bot difficulties: Beginner (depth 1), Intermediate (depth 8), Advanced (depth 14) — tuned after spike.
  • Game state: Chess instance in memory; persist to DB on exit or game end.
  • Post-game: link to analysis view with local PGN.

4.2 Game Analysis

  • Import paths: paste PGN, pick local saved game, fetch by Lichess game ID/URL, fetch Chess.com game (username + date or PGN download URL).
  • Replay UI: move list, keyboard/gesture prev-next, jump to position, flip board.
  • Engine overlay: eval bar, best move arrow (optional), blunder markers on move list (Phase 2).
  • Parse with domain PgnService; normalize to internal GameRecord model.

4.3 Openings Trainer

  • Seed data: ECO-grouped opening lines as bundled JSON/SQLite (100–200 lines for MVP).
  • Drill mode: app plays opponent moves; user plays correct responses; hints after N failures.
  • Progress: per-line completion %, last practiced date (spaced repetition lite).

4.4 Tactics Trainer

  • Puzzle source: bundled Lichess puzzle dump subset (filtered by rating band) or CSV import.
  • Modes: daily puzzle (1/day), practice queue (10 puzzles), timed rush (Phase 3).
  • Feedback: correct/incorrect animation, solution line reveal, puzzle rating adjustment locally.

4.5 Square Name Mini-Game

  • Modes: Find square (prompt → tap), Name square (tap → type/select), Timed blast (30s score attack).
  • Orientation toggle: white-bottom / black-bottom.
  • Scoring: accuracy %, best streak, personal bests stored locally.
  • Low implementation cost — good Phase 1 quick win for engagement.

9. Monetization Hypothesis

Every build should have a plausible validation path. Recommended model:

  • Free tier: Play vs bot (limited daily games), square trainer, 3 puzzles/day, basic analysis.
  • Pro subscription (~$4.99/mo): Unlimited games, full tactics queue, openings repertoire, deep engine analysis, no ads.
  • Validation metric: 7-day retention on users who complete ≥1 bot game + ≥1 training session.

Defer payment integration until Phase 2 proves retention. Use local feature flags to gate Pro features during development.
